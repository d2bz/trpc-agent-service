## 2. 两个项目的边界差异

cc-connect 面向“本地编码助手连接办公 IM”。其平台对象接收消息后，可以直接把进程内 `Message` 和 `replyCtx` 交给本地 Agent Engine，并依赖本机 Session 与短期内存去重。

本项目面向多租户 Agent 服务平台。Channel Adapter 只是外部协议边界，消息进入后必须经过：

```text
IM callback / WebSocket event
    -> Channel Adapter
    -> InboundEnvelope
    -> PostgreSQL Inbox
    -> Redis Stream wake-up
    -> Worker / tRPC-Agent-Go Runner
    -> PostgreSQL Outbox
    -> Channel Sender
```

因此，可参考范围只覆盖接收、解析、媒体、格式、平台限流和发送；租户路由、Revision、Session、Run、幂等和故障恢复仍由本项目平台层负责。

## 3. 上游概念到本项目的映射

| cc-connect 概念 | 本项目承接位置 | 处理方式 |
| --- | --- | --- |
| `Platform.Start` | Channel Receiver 生命周期 | 拆分连接管理和入站提交，不直接调用 Agent |
| `core.Message` | `InboundEnvelope` | 生成稳定的外部事件、发送者、会话、话题和媒体标识 |
| `replyCtx any` | 持久化的 `DeliveryTarget` | 使用可校验、可序列化的类型，随 Outbox 保存 |
| `Reply` / `Send` | Channel Sender | 输入 Outbox attempt，返回结构化发送结果 |
| 进程内 `MessageDedup` | PostgreSQL Inbox 唯一约束 | 去重跨进程、跨 Worker、跨重启有效 |
| goroutine 调 MessageHandler | Inbox + Dispatcher | 回调不能启动无界 Agent 执行 goroutine |
| 本地 `SessionKey` | Principal/Conversation/Thread 到 Session 的映射 | 加入 Tenant 和 Channel Binding 作用域 |
| Platform 内凭据 | Secret Resolver + Channel Runtime | 数据库只保存 `secret_ref`，日志不输出密钥 |
| 发送函数内部重试 | Outbox attempt 状态机 | 区分可重试、永久失败和结果未知 |

`DeliveryTarget` 至少要保存重新发送所需的真实平台目标，例如飞书 `chat_id/message_id/thread_id` 或企微的用户、群聊与 Agent 标识。不能只保存哈希，也不能依赖已失效的进程内 `replyCtx`。

## 4. 跨平台可借鉴项

### 4.1 连接与生命周期

- 长连接需要启动、就绪、降级、重连和停止状态，不能把 `Start` 返回成功等同于已经可接收流量。
- 重连采用有上限的退避，并在稳定连接一段时间后重置退避。
- 心跳需要检测连续丢失的 ACK/Pong，不能只记录发送 Ping 成功。
- 停止时取消后台 goroutine、关闭连接、清理等待 ACK 的请求，避免泄漏和悬挂发送。
- 相同平台应用凭据建立多条连接时，要核实平台的负载均衡语义。飞书相同 App 的多个 WebSocket 可能分摊事件，不应假设每条连接都收到完整副本。

### 4.2 入站标准化

- 单聊、群聊、话题/线程和引用消息必须分别建模，不能只拼一个不可逆的字符串 Session Key。
- 明确区分“当前用户指令”和“被引用内容”，避免引用文本被误认为新指令。
- 处理只包含 @、只包含附件、引用附件、批量图片和混合媒体的消息。
- 平台 message/event ID 用作外部幂等键；缺失时必须有明确降级策略，不能用正文哈希冒充可靠事件 ID。
- 媒体元数据先入 Inbox，下载可按平台回调时限选择同步或后台进行，但失败状态必须可恢复、可观测。
- 群聊是否必须 @机器人以及允许哪些群，应由 Channel Binding 策略控制；身份探测失败时默认 fail closed。

### 4.3 出站发送

- 按平台的 UTF-8 字节限制拆分文本，不能按 rune 数或字符显示宽度判断。
- 优先在段落、换行或句子边界拆分；最终硬切也必须保持合法 UTF-8。
- Markdown、富文本和卡片要有平台能力判断与纯文本降级路径。
- Token 失效可刷新后重试一次；网络瞬时错误使用有界退避；明确的业务拒绝不能盲目重试。
- `429`、平台错误码、HTTP 状态、超时和连接中断应映射为统一错误分类，并尽量保留 `Retry-After`。
- 每个 Outbox part 使用稳定的业务幂等键和独立 attempt；第 N 段失败不能导致前 N-1 段重新生成或重新运行 Agent。
- 发送超时且平台未提供查询或客户端消息 ID 时，结果应标为 ambiguous/`duplicate_risk`，不能直接记为成功或永久失败。

### 4.4 媒体与安全

- 下载和上传设置正文大小、文件数量、分块数、单块大小、总耗时及 MIME 类型限制。
- 文件名、message ID 和 Content-Disposition 都是不可信输入，必须防止路径穿越和静默覆盖。
- 远程图片下载需要 SSRF 防护，禁止私网、环回、链路本地和保留地址，并在重定向后重新校验。
- 平台 URL 中的 token、ticket、secret、key、device ID 等参数在日志中脱敏。
- 不记录解密后的完整消息、凭据或完整敏感正文；调试预览也应受环境和长度约束。
- 媒体下载失败不应丢失整个 Inbox 事实，应保留错误码和可重试状态。

## 5. 飞书专项参考

实现飞书 Adapter 时，优先核对以下行为：

1. 使用飞书官方 Go SDK 接收事件和调用 API，并固定、记录经过验证的版本。
2. 按 App 凭据共享 WebSocket 连接时，将事件分发到对应 Channel Binding；不得把不同 Tenant 的绑定混在无作用域的全局表中。
3. 启动时获取机器人 `open_id`。获取失败时，单聊可按策略继续，群聊过滤必须 fail closed，并由后台任务恢复探测。
4. 同时覆盖单聊、群聊、话题根消息、回复线程、引用消息、机器人 @ 和 `@all`。
5. Token 无效和瞬时网络错误采用不同重试路径，避免每种 API 各自实现不一致的重试逻辑。
6. 大文件资源下载验证 Range、`Content-Range`、总长度、分块一致性、取消和最大体积。
7. 富文本链接只允许平台支持的协议；非法链接降级为普通文本，避免整条消息被平台拒绝。
8. 卡片发送、更新和限流与普通文本分开分类；第一版可以使用文本/富文本闭环，不让卡片预览拖累核心验收。
9. 多张图片短时间连续到达时，核实平台是否拆成多个事件；是否聚合必须由显式窗口和顺序规则决定。
10. 互动卡片回调也要进入统一 Inbox，不能绕过租户路由和持久幂等。

## 6. 企业微信专项参考

企业微信可使用 WebSocket 长连接或 Webhook，两种模式共享标准化和 Outbox 接口，但接收端生命周期不同。

### 6.1 Webhook

- URL 验证需要校验签名、解密 `echostr` 并验证 CorpID。
- 消息回调依次执行请求体限长、XML 解析、签名校验、AES-CBC 解密、PKCS#7 校验、消息长度校验和 CorpID 校验。
- 必须在平台规定时限内响应，但本项目只有在 Inbox 首次插入成功或确认已存在后才能回复“已受理”。
- cc-connect 在完成解密后立即返回 200、再解析和进程内处理，这一点不适用于本项目，不能照搬。

### 6.2 WebSocket

- 实现连接订阅、心跳、连续丢失 Pong 判死、指数退避重连和可取消停止。
- 使用稳定且并发安全的请求 ID，将发送请求与 ACK 对应。
- ACK 超时属于结果未知；不能简单“继续并视为成功”，应交给 Outbox 状态机判断重试和重复风险。
- 连接重建时清理或失败化旧连接上的 pending ACK，防止调用永久等待。
- 媒体上传的初始化、分块、结束和最终发送分别检查 ACK，并限制最大分块数。

### 6.3 按接入模式选择发送认证

- 仅使用 HTTP access token 的接入模式按官方 `expires_in` 缓存和刷新；智能机器人长连接使用订阅认证，不执行这套流程。
- HTTP 模式遇到明确的 Token 失效码时清缓存并最多刷新重试一次；长连接认证失败或被替换时按其连接协议处理。
- 文本按企业微信的字节限制拆分，覆盖中文、多字节字符和边界值。
- Markdown 能力按具体消息类型配置，不默认所有企业微信客户端都一致渲染。

## 7. 明确不采用的上游做法

- 不采用 `map[string]any` 作为长期 Channel 配置契约。
- 不采用全局 `init` Registry 隐式注册平台。
- 不采用 `replyCtx any` 在接收与发送之间传递目标。
- 不采用 60 秒进程内 Map 作为最终消息去重机制。
- 不采用“进程启动时间之前的消息全部丢弃”作为重启恢复策略。
- 不在回调中直接启动无界 goroutine 调用 Agent。
- 不把凭据长期写入共享 Platform 对象或日志字段。
- 不把发送失败处理成重新运行 Agent。
- 不把本地编码助手的命令、工作目录、流式预览卡片等特性纳入第一版 Channel 核心接口。
- 不将巨型单文件 Adapter 作为扩展模板；协议、标准化、发送、媒体和生命周期应保持可独立测试的边界。

## 8. 实现前要固定的本项目契约

进入编码前，由 Leader 明确以下契约，再交给实现负责人：

1. `InboundEnvelope` 的必填字段、外部事件唯一键和消息/媒体表示。
2. Channel Binding 如何从外部账号确定 Tenant、Agent App 和身份映射。
3. Receiver 将事件提交 Inbox 后的成功、重复、临时失败和永久拒绝语义。
4. 可持久化 `DeliveryTarget` 的版本化结构及敏感字段边界。
5. Sender 的结果类型：成功、可重试、永久失败、限流、认证失效和结果未知。
6. Inbox `claim_token`、Run 状态、Outbox `send_token` 与平台 ACK 的关系。
7. 文本分片、媒体对象、引用/线程回复和主动发送的 Outbox 表达。
8. Adapter 生命周期、健康状态、凭据轮换和多副本所有权。

## 9. 测试清单

### 9.1 协议与安全

- 正确与错误签名、密文截断、非法 padding、错误 CorpID、超大请求体。
- Token/Secret 日志脱敏，解密正文不进入普通日志。
- SSRF、重定向到私网、路径穿越、重复文件名和超大媒体。
- 身份探测失败、群聊过滤降级和跨 Tenant Channel Binding 隔离。

### 9.2 消息标准化

- 单聊、群聊、话题、引用、仅 @、`@all`、仅附件和混合消息。
- 平台重复事件在同进程、跨 Worker、重启后都只生成一个 Inbox。
- 同一会话消息顺序、不同会话并行以及消息时间戳相同的情况。
- 回复目标序列化后跨进程恢复发送。

### 9.3 连接与故障恢复

- 首次连接失败、稳定后断线、连续心跳丢失、退避上限和正常停止。
- 多绑定共享同一 App 凭据、不同 App 隔离以及连接所有者重启。
- Inbox 已提交但 Redis 通知失败，由扫描器重新投递。
- Worker 处理中断不会导致 Channel 回调重新运行已完成的 Agent。

### 9.4 出站与媒体

- ASCII、中文、emoji 和组合字符在字节边界拆分后仍为合法 UTF-8 且可重组。
- 第 N 个分片失败只重试对应 Outbox part。
- Token 过期刷新、429、5xx、连接重置、超时、永久业务错误和 ACK 结果未知。
- 媒体分块边界、服务端总长度不一致、取消、重试和最大体积。
- Session 已提交而发送失败时，只重试 Outbox，不重新调用 Runner。

## 10. 后续使用步骤

做到 IM 模块时按以下顺序使用本文：

1. 依据本项目架构固定 Channel/Inbox/Outbox 契约。
2. 查阅当时最新的飞书或企业微信官方文档与 SDK。
3. 对比本文及 cc-connect 对应平台实现，补充遗漏的协议边界。
4. 只选择当前验收需要的最小能力集，先形成真实纵向链路。
5. 把选中的边界场景写成本项目测试，不以“上游已测试”代替自己的证据。
6. 完成多 Worker、重启恢复、重复投递和发送失败演示后，再扩展卡片、复杂媒体与主动消息。
